# Правила работы

Проект: «Кошки против собак», физическая 2D-игра на Godot для ПК и телефонов.
Общение и документация — по-русски; код, имена файлов и идентификаторы — по-английски.

## Минимальный контекст

1. В начале задачи прочитай этот файл и `docs/STATUS.md`.
2. Открывай только нужные для задачи файлы. Не перечитывай всю документацию.
3. Архитектура, решения и карта файлов: `docs/PROJECT.md`.
4. Запуск, проверки, экспорт: `docs/WORKFLOW.md`. Первый запуск: `README.md`.
5. Если статус расходится с кодом, проверь код и исправь краткую запись в статусе.

## Работа с кодом

- Используй типизированный GDScript, сцены `.tscn` и ресурсы `.tres`.
- Следуй стилю соседнего кода: табуляция, `snake_case`, небольшие функции.
- Для игровой логики предпочитай композицию узлов и сигналы.
- Добавляй зависимости, плагины, autoload и абстракции при конкретной необходимости.
- Параметры уровня храни в `levels/`, общие параметры объектов — в экспортируемых свойствах.
- Сохраняй управление мышью и касанием; избегай дублирования синтетических событий.
- Проверяй интерфейс в горизонтальных окнах разных пропорций, включая узкие экраны.
- Физика работает с фиксированным шагом; не привязывай её к частоте отрисовки.
- Сохраняй оригинальный стиль и собственные ассеты; сейчас графика процедурная.
- Не добавляй backend, рекламу, аналитику или покупки без отдельной задачи.

## Экономия контекста

- Для поиска используй `rg` по конкретным папкам и ограничивай вывод.
- Исключай `.godot/`, `.tools/`, `.artifacts/`, `build/` и импортированные бинарные файлы из обзора.
- В Windows PowerShell читай русский текст через `Get-Content -Encoding UTF8`.
- Не печатай целые большие файлы, рекурсивные деревья и повторные успешные логи.
- Перед изменением найди владельца поведения по карте файлов.
- Заверши одну рабочую вертикаль до расширения инфраструктуры.
- Независимые чтения и проверки можно объединять; зависимые изменения делай последовательно.

## Проверка и передача

- После изменения кода запусти `tools/check.ps1` согласно `docs/WORKFLOW.md`.
- Для изменения только текста достаточно проверить ссылки и соответствие коду.
- Добавляй тесты для существенного поведения и исправленных ошибок; не дублируй реализацию.
- После изменения механики вручную проверь затронутый сценарий и мышь/касание при необходимости.
- Не выдавай headless-проверку за тест телефона, графики или готовой сборки.
- Не коммить `.godot/`, сборки, локальные SDK, ключи и пароли подписи.
- Обновляй `docs/STATUS.md`, когда меняется готовность, ограничение или следующий шаг.
- При изменении архитектуры, запуска или договорённостей обновляй соответствующий документ.
- Документы содержат актуальное состояние, а не хронологию каждого действия.
- Итог задачи: что готово, что проверено, существенные ограничения — коротко.
